# T02: 功能实现 (Feature Implementation)

## 场景描述

实现新的功能特性或完成产品需求中定义的功能模块。这是最常见的开发任务，需要将产品需求转化为可工作的代码实现。

## 何时使用

**触发场景**：
- 产品需求明确，需要编写实现代码
- 开发计划中的功能开发任务
- 用户故事需要转化为具体实现

**触发短语**：
- "实现功能"
- "开发需求"
- "编写代码完成XXX"
- "实现XXX特性"
- "按照需求开发"

**前置条件**：
- `Product-Spec.md` 已明确定义需求
- `DEV-PLAN.md` 中有当前阶段的任务定义
- 设计方案已确定（如需要）

```

- 错误处理：包含完整的异常处理和错误提示
- 边界条件：处理空值、边界值、异常输入
- 代码注释：关键逻辑添加清晰注释
- 复杂度标注：关键算法标注时间和空间复杂度

**质量要求**：
- 通过项目的lint检查（ESLint/Pylint/Checkstyle等）

- 包含单元测试或提供验证证据

**不要做的事**：
- 不做假数据或假按钮（所有UI元素必须是功能性的）
- 不修改或删除共享代码（除非确认影响范围）
- 不引入不必要的依赖或库
- 不复制粘贴大段重复代码
```

```python
    """
    def find_by_id(self, user_id: int) -> Optional[User]:
        """
        根据ID查找用户
        时间复杂度: O(1) - 数据库索引查找
        空间复杂度: O(1)
        """
        # 实现数据库查询
        pass

    def save(self, user: User) -> User:
        """保存用户"""
        pass

class UserService:
    """
    用户业务逻辑层（依赖倒置原则）
    依赖抽象的Repository接口，而非具体实现
    """
    def __init__(self, repository: UserRepository):
        self.repository = repository

    def get_user(self, user_id: int) -> Optional[User]:
        """
        获取用户信息
        包含错误处理和边界条件检查
        """
        if user_id <= 0:
            raise ValueError("用户ID必须为正整数")

        user = self.repository.find_by_id(user_id)
        if user is None:
            raise UserNotFoundError(f"用户 {user_id} 不存在")

        return user

# 使用示例
repository = UserRepository()
service = UserService(repository)  # 依赖注入
user = service.get_user(123)
```

## 质量检查清单

在实现完成后，使用此检查清单进行自检：

### 功能完整性
- [ ] 所有需求点都已实现
- [ ] 边界条件已处理（空值、空数组、边界值）
- [ ] 错误情况已考虑（网络错误、数据库错误、权限错误等）
- [ ] 用户交互流程完整（成功路径+失败路径）

### 代码质量
- [ ] 符合SOLID原则
  - [ ] 单一职责：每个类/函数职责明确
  - [ ] 开闭原则：通过扩展而非修改实现新功能
  - [ ] 里氏代换：子类可安全替换父类
  - [ ] 接口隔离：接口小而专注
  - [ ] 依赖倒置：依赖抽象而非具体实现
- [ ] 代码复用：优先使用了现有组件和工具
- [ ] 命名清晰：变量名、函数名、类名具有描述性
- [ ] 注释适当：复杂逻辑有注释说明

### 性能与安全
- [ ] 算法复杂度合理，无明显性能瓶颈
- [ ] 关键算法标注了时间和空间复杂度
- [ ] 没有SQL注入、XSS等安全漏洞
- [ ] 敏感数据已加密或脱敏

### 测试与验证
- [ ] 包含单元测试或集成测试
- [ ] 测试覆盖主要路径和边界情况
- [ ] 通过所有现有测试（没有破坏现有功能）
- [ ] 提供了手动验证步骤和结果

### 文档与规范
- [ ] 通过lint检查
- [ ] 遵循项目编码规范
- [ ] API或接口有必要的文档
- [ ] 如有配置变更，已更新相关文档

## 常见问题与解决方案

### 问题1：需求不明确
**症状**：不确定某个功能应该如何实现
**解决**：
1. 重读 `Product-Spec.md`，查找相关说明
2. 检查是否有设计文档或原型
3. 如仍不明确，向用户提出具体问题（而非猜测实现）

### 问题2：与现有代码冲突
**症状**：新功能与现有实现存在冲突或重复
**解决**：
1. 全局搜索相关代码，了解现有实现
2. 优先复用现有组件和接口
3. 如需修改共享代码，先评估影响范围
4. 考虑使用策略模式或工厂模式扩展而非修改

### 问题3：性能担忧
**症状**：算法复杂度过高或预期数据量大
**解决**：
1. 明确数据规模和性能目标
2. 分析当前实现的时间和空间复杂度
3. 考虑优化方案：
   - 数据结构优化（如用哈希表替代数组查找）
   - 算法优化（如用动态规划替代递归）
   - 缓存策略（如Redis缓存热点数据）
   - 异步处理（如消息队列处理耗时任务）

### 问题4：测试困难
**症状**：不知道如何测试或测试用例不好写
**解决**：
1. 确保代码遵循单一职责原则（易测试的信号）
2. 使用依赖注入，方便mock外部依赖
3. 将复杂逻辑拆分为小函数，分别测试
4. 至少覆盖：正常路径、边界条件、错误情况

## 使用示例

### 示例1：简单功能实现

**用户请求**：
"实现一个用户注册功能，需要验证邮箱格式和密码强度"

**应用此模板**：

```
## Context
项目背景：用户管理系统，使用Python + Django + PostgreSQL
当前任务：实现用户注册API
相关需求：Product-Spec.md 第3.1节 - 用户注册
业务上下文：允许新用户注册账号，确保数据合法性
技术约束：
- Python 3.9+, Django 4.0+
- 响应时间 < 200ms
- 密码必须加密存储

## Role
你是一位资深的Python/Django工程师，擅长Web API开发和数据验证。

## Instruction
请实现用户注册功能：
1. 创建REST API端点 POST /api/users/register
2. 验证邮箱格式（RFC 5322标准）
3. 验证密码强度（至少8字符，包含大小写字母和数字）
4. 密码使用bcrypt加密
5. 邮箱重复时返回明确错误
6. 包含单元测试

技术要求：
- 符合SOLID原则
- 使用Django REST framework
- 完整的错误处理
- 通过flake8检查

## Sample
[提供Django视图和序列化器示例]

## Expectation
输出格式：
- views.py: 注册视图实现
- serializers.py: 数据验证
- tests.py: 单元测试
- 验证命令：python manage.py test

性能要求：O(1)数据库查询
代码风格：PEP 8
```

### 示例2：复杂功能实现

**用户请求**：
"实现一个实时搜索功能，支持模糊匹配，数据量约100万条"

**关键调整**：
- Context中强调数据规模（100万条）和实时要求
- Instruction中增加性能约束（如响应时间<100ms）
- 在算法选择部分建议使用Elasticsearch或前缀树
- Expectation中明确复杂度要求（如 O(log n) 查找）

## 附录：CRISPE框架速查

| 元素 | 含义 | 关键问题 |
|-----|------|---------|
| **C**ontext | 上下文 | 背景是什么？在什么环境下？ |
| **R**ole | 角色 | 你是谁？有什么专长？ |
| **I**nstruction | 指导 | 要做什么？怎么做？ |
| **S**ample | 示例 | 参考什么？最佳实践是什么？ |
| **E**xpectation | 预期 | 产出格式？完成标准？ |

**使用技巧**：
- **具体>模糊**："响应时间<100ms" 好于 "要快"
- **上下文完整**：提供背景、约束、目标
- **约束明确**：性能、安全、兼容性要求
- **预期清晰**：格式、风格、包含内容
- **可验证**：提供检查清单和验证步骤
