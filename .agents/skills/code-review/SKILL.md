# 代码审查

## 核心

执行两阶段审查。第一阶段检查是否做对需求，第二阶段检查实现是否值得保留。

## 输入

- `Product-Spec.md`。
- `DEV-PLAN.md`。
- 相关的 `Design-Brief.md` 或设计产物。
- 差异和变更文件。

## 产出

- 第一阶段通过/失败结论。
- 第一阶段通过后，给出第二阶段通过/失败结论。
- 带证据和文件引用的问题清单。

## 规则

- 审查时不修复。
- 每个结论都必须有证据。
- 第一阶段有阻塞问题时停止，不进入第二阶段。
- 检查测试真实性，不只看有没有测试。
- 检查界面引导真实性：可见说明必须对应真实行为。

## 检查清单

### 需求正确性
- [ ] 需求已映射到实现证据。
- [ ] 缺失或部分完成的工作已列出。

### 工程质量
- [ ] 质量风险已按严重程度排序。
- [ ] 审查结论明确。

### SOLID原则快速检查

**单一职责原则 (S)**
- [ ] 每个类/模块的职责单一且明确
- [ ] 类名准确反映其唯一职责
- [ ] 修改的理由只有一个

**开闭原则 (O)**
- [ ] 新功能通过扩展（继承/组合）而非修改实现
- [ ] 核心逻辑依赖抽象而非具体实现
- [ ] 使用了策略模式、工厂模式等扩展友好的设计

**里氏代换原则 (L)**
- [ ] 子类可以安全替换父类
- [ ] 子类没有违反父类的契约（前置/后置条件）
- [ ] 子类没有抛出父类未声明的异常

**接口隔离原则 (I)**
- [ ] 接口足够小且专注（避免"胖接口"）
- [ ] 类不被迫实现不需要的方法
- [ ] 接口职责清晰单一

**依赖倒置原则 (D)**
- [ ] 高层模块不直接依赖低层模块，两者都依赖抽象
- [ ] 抽象不依赖细节，细节依赖抽象
- [ ] 使用了依赖注入或接口抽象
